工程规范基线架构与自动化发版设计全貌

长图

答

结论

多技术栈工程治理采用分层 Provider 架构，发布全流程采用声明式 Release PR 自动化，实现业务开发与版本发布彻底隔离。

  1. 核心基线单一源头管理，语言特性与可见性策略按需注入。
  2. 彻底废除本地发布脚本，发版 PR 严格仅改动版本号与变更日志。
  3. Rust 接入原生的 release-plz，发版自动同步锁文件，终结门禁死锁。
  4. 统一 gate 合并门禁，全技术栈固定 40 位 SHA 供应链安全。

适用于RustBunuvPublicPrivaterelease-plzrelease-please

系统架构与 Provider 如何分层协作？

图的结构
  • CLI 调度器 cli
  • 智能探测器 detect
  • 通用基线 Core core
  • 技术栈 Provider stacks
  • 可见性 Provider vis
  • CI/CD 工作流 actions
  • GitHub 远端配置 remote
  • cli → detect · 分析目标特征
  • detect → core · 组装通用文件
  • detect → stacks · 注入语言模板
  • detect → vis · 匹配开源策略
  • stacks → actions · 部署流水线
  • core → remote · 同步规则与标签
  1. CLI 调度器 ↗

    接收用户或 Agent 指令，驱动本地应用与远端同步。

  2. 智能探测器 ↗

    扫描清单文件识别 Rust、Bun、uv，探测远端可见性。

  3. 通用基线 Core ↗

    分发提交规范、Issue 与 PR 模板、标签字典与忽略基线。

  4. 技术栈 Provider ↗

    差异化注入 CI/CD 流水线与语言特化配置文件。

  5. 可见性 Provider ↗

    注入开源 MIT 协议或商业专有保密版权声明。

  6. GitHub 远端配置 ↗

    同步 Ruleset 分支保护、清理非标标签、配置 Actions 权限。

发版流程如何实现功能与发布物理隔离？

图的结构
  • 开发者 dev
  • main 分支 main
  • Release 机器人 bot
  • 发版 PR pr
  • GitHub Release release
  • dev → main · 提交功能 PR (约定式提交)
  • main → bot · 触发 release 扫描
  • bot → pr · 自动生成版本与更新日志
  • dev → pr · 审查版本变更内容
  • dev → pr · 确认无误，点击 Merge
  • pr → main · 合并发版 PR
  • main → release · 自动创建 Tag 与发布版本
  • release → dev · 编译挂载跨平台安装包
  1. 业务开发阶段 ↗

    日常提交遵循约定式提交规范，功能代码通过常规 PR 合入主干。

  2. 发版 PR 维护 ↗

    机器人监听主分支推送，自动扫描未发版提交并维护唯一的发版 PR。

  3. 纯净版本差异 ↗

    发版 PR 中严格仅有版本清单与 CHANGELOG 的改动，零业务代码污染。

  4. 人工合并发版 ↗

    维护者随时审查版本内容，准备发版时只需点击 Merge。

  5. 跨平台构建分发 ↗

    PR 合并自动生成 Git Tag，触发矩阵编译并挂载 Release 附件。
